# Benchmarks

Measured, not estimated. Every table in this file is generated by
`bench/report.py` from the JSON that `bench/suite.py` wrote, so re-running the
suite updates the numbers instead of leaving a stale claim in the docs.

## What was measured, and how

The published suites disagree on almost everything except the metrics, so the
metrics are what this follows:

| suite | what it contributes here |
|---|---|
| ANN-Benchmarks | recall@k against a brute-force scan, plotted against QPS |
| VectorDBBench | p99 latency, per-query recall distribution (min, p1, p5), filtered search, concurrency |
| Weaviate's ANN benchmark | build time, index size, mean and p99 latency, 10k-request runs |

Not measured, and why:

| not measured | why |
|---|---|
| SIFT1M, GIST1M, Cohere-10M, LAION-100M | they are multi-GB downloads; this sandbox has no route to them. The shapes are reproduced synthetically instead, and the `skewed` and `isotropic` rows are the adversarial ones |
| HNSW / DiskANN / IVF-PQ as competitors | out of scope: this compares the store's own two engines against each other and against RagForge |
| MTEB / BEIR retrieval quality | those measure an embedder, not an index. With the default `hash` embedder there is nothing to score; that is a separate job with a real model |
| monetary cost per query (QP$) | needs cloud pricing, which changes monthly |

### Hardware and the noise floor

Every number below comes from a **2 vCPU, 2 GB Linux container**, the same class
as the box RagForge published its table on. It is shared, and it is noisy:

- the same exact-scan query measured **3.5 s** and **14 s** on two runs an hour apart
- p99 latencies carry the pod's scheduling tail; p50 is the number to trust
- index-only measurements (in-memory, many repetitions) are stable to ~10%;
  anything touching SQLite or the filesystem is stable to ~30%

Read every figure as "on this machine, at this moment". The ratios hold; the
absolute milliseconds do not travel.

## Through SQLite: what a real query costs

200,000 x 128, index rebuilt in 29.1 s at 105.0 MB.

| stage | p50 ms | p95 ms | p99 ms | samples |
|---|---|---|---|---|
| vector signal (native index, default nprobe) | 18.512 | 62.471 | 64.692 | 120 |
| full `retrieve()`: BM25 + vector + address + fusion | 82.6 | 91.9 | 91.9 | 5 |

The gap between the two rows is the part of retrieval that is not the vector index: FTS5 over the chunk text, the address ranking, and the join that hydrates each hit with its citation. At 200k chunks that work is tens of milliseconds and it is now the larger half — the index is no longer the bottleneck it was built to remove.

## Concurrency

200,000 x 128, nprobe 40.

| threads | queries | QPS | p50 ms | p95 ms | p99 ms |
|---|---|---|---|---|---|
| 1 | 60 | 75.9 | 6.9 | 52.26 | 54.11 |
| 2 | 120 | 70.3 | 20.26 | 72.51 | 99.49 |
| 4 | 240 | 52.5 | 58.82 | 179.73 | 302.06 |

Throughput **falls** as threads are added: 2 vCPU, one Python process, and a rescore that touches SQLite. NumPy releases the GIL for the matmul, but the gather, the dequantise and the SQLite read are Python-bound, so extra threads buy contention, not throughput. Serve this process with one worker per core, not more.

## What the benchmark found

Benchmarking is how the two worst defects in this code were found, and both were
invisible to the tests:

**1. The freshness check was the query.** `is_stale()` called
`vector_fingerprint()`, which is `SELECT COUNT(*), MAX(chunk_id) FROM vectors`
-- an O(n) scan, **1,814 ms** at 200k rows, on *every* query, because the router
asks "is the index stale?" before each one. The index was doing 2 ms of work
behind a 1.8 s gate.

Fixed with a monotone revision counter in the `meta` table, bumped by
`set_vector` and `clear_vectors`, read in 0.7 ms. Native query latency at the
default `nprobe`: **3,325 ms -> 18.5 ms**. The tests passed before and after,
because a test store is far too small for an O(n) scan to show up.

**2. The vector signal is no longer the bottleneck.** With the index at 18.5 ms,
full `retrieve()` costs 82.6 ms at 200k chunks. The difference is BM25, the
address ranking, and the join that hydrates each hit. `_address_ranking` calls
`store.addresses()`, which selects every addressed chunk and parses 200k
`Address` objects per query. That is the next thing to fix, and at this point it
is worth more than any further work on the index.

## Tuning, from these numbers

| if you see | change |
|---|---|
| p50 above ~20 ms at 200k | `ann.nprobe: 2` -- 100% recall@10 on clustered and near-duplicate corpora at 1.3 ms |
| recall below 90% on a long-tail corpus | raise `nprobe`, or set `ann.mode: off` and accept the scan |
| recall below 40% on any corpus | the embedder is the problem, not the index: `hash` produces near-random directions |
| RAM pressure | `ann.dtype: int8` (4x smaller, one conversion per scored row) |
| more than one worker process | one per core, not more: throughput falls with threads on this box |
| slow first query after start | the index loads off disk; it is a startup cost, warm it |

## Retrieval quality: does the vector mean anything?

Every table above was measured with the `hash` embedder, which is a feature hash
and not a meaning. That makes those numbers a statement about the **index** —
does routing find the vector the scan would find — and not about **retrieval**.

`bench/embedders.py` measures the second thing on a small labelled set: the
repository's own documentation, one topic per file, and 12 queries phrased the
way a person would phrase them, deliberately **avoiding the words the target
document uses** — a query that repeats the title only tests the keyword index.

### One vector per document

| system | recall@1 | recall@3 | MRR |
|---|---|---|---|
| bm25 (FTS5, OR + bm25 ranking) | 17% | 42% | 0.292 |
| hash (the old default) | 17% | 42% | 0.322 |
| **model2vec (potion-base-8M)** | **33%** | **50%** | **0.472** |

At document granularity the semantic embedder **doubles recall@1**. That is the
case embeddings exist for: a 12,000-character file mean-pooled into 256 numbers
still lands nearer the right query than a keyword overlap does.

### Chunked at 500 characters — what the store actually holds

| system | recall@1 | recall@3 | MRR |
|---|---|---|---|
| bm25 | 25% | 58% | 0.433 |
| hash | 17% | 33% | 0.274 |
| model2vec | 17% | 58% | 0.447 |
| bm25 + hash (fused by RRF) | 8% | 67% | 0.359 |
| **bm25 + model2vec (fused by RRF)** | **25%** | **75%** | **0.524** |

Three findings, in order of how much they matter:

1. **At chunk level, keywords win on their own.** BM25 gets 25% recall@1 where
   the vector gets 17%. A 500-character chunk contains the words; dilution is
   what embeddings fix, and a chunk has little to dilute.
2. **Fusion is where the semantic signal pays.** BM25 + model2vec reaches **75%
   recall@3 against BM25's 58%**, and MRR 0.524 against 0.433. That is the
   configuration `retrieve()` actually runs.
3. **The old default was not neutral — it was harmful.** BM25 + hash scores
   **8% recall@1**, worse than BM25 alone (25%). A lexical hash adds a second
   copy of the same evidence, and RRF then double-counts it. Replacing `hash`
   with a real embedder is not a refinement; the previous default was actively
   costing recall.

### The honest caveats

- **12 queries, 15 documents.** Small enough to check by hand, which is why the
  script prints a per-query audit: two of the labels are arguable (both
  "what am I allowed to do" queries point at `RULES.md`, and "run on a laptop"
  could reasonably be `BENCHMARKS.md`), so the absolute numbers are soft. The
  *ordering* between systems is consistent across both granularities.
- **These are documentation pages**, not a corpus of questions people asked.
- **model2vec is uncontextualised**: it averages a static table, so word order
  and negation are invisible to it. It won here anyway.

```bash
pip install model2vec
python bench/embedders.py      # the three tables above, from this machine
```

## The address signal: 349 ms to 2.5 ms

`docs/BENCHMARKS.md` named the address ranking as the largest remaining cost in
the retriever. `bench/address.py` measures the two implementations on the same
store — 20,000 chunks, each with a five-part address:

| implementation | p50 | max |
|---|---|---|
| python loop over `store.addresses()` (before) | **349.2 ms** | 376.1 ms |
| cached integer matrix + numpy (after) | **2.46 ms** | 2.78 ms |

**142× faster, and the results are identical** — the script asserts that, and so
does `tests/test_address_ranking.py`, which compares the vectorised rule against
`semantic_similarity` for five different hints, with and without centroids.

Two things made it slow, and both were avoidable:

1. **Every address was parsed from its string on every query.** `Address.parse`
   ran 20,000 times per query. The five numeric parts were already columns in
   `chunks` (`addr_domain`, `addr_family`, `addr_kind`, `addr_cluster`,
   `addr_ordinal`) — the string was being parsed to recover what the schema
   already had.
2. **`semantic_similarity` ran once per chunk in Python.** The rule is four
   comparisons and a dot product; it vectorises completely.

### The freshness check, done right this time

The matrix has to be invalidated when a chunk changes, and wave 7's lesson was
that asking "has anything changed?" with a `COUNT(*)` costs more than the thing
being guarded. So the revision is a `meta` counter maintained by **SQLite
triggers** on `chunks` (insert and update) — every write path bumps it, including
the ones that are raw SQL in `passes.py` and would have been missed by hand.

```
cold query (first after a write)   ~350 ms   materialises the matrix
warm query                          ~2.5 ms   matrix reused
```

The first query after a write pays for the materialisation, which is the same
trade as the vector index: build once, query many. In `vrusha serve` it is paid
once; in a one-shot CLI it is paid once per command, which is still cheaper than
the old cost on any store above a few thousand chunks.

```bash
python bench/address.py            # both numbers, from this machine
ADDRESS_BENCH_CHUNKS=200000 python bench/address.py
```

## On real embeddings, not synthetic shapes

Every recall table above came from `bench/suite.py`, which *generates* vectors.
Those shapes are worth having — they are the adversarial cases a vendor would
rather not publish — but they are guesses about what an embedder produces.
`bench/real_corpus.py` replaces the guess with the thing: **2,373 chunks from
this repository**, embedded with `model2vec`, and the same index measured against
the same brute-force reference.

### The geometry first, because it explains the curve

| statistic | value |
|---|---|
| chunks × dim | 2,373 × 256 |
| mean cosine between two random chunks | **0.462** |
| p95 cosine | 0.624 |
| mean nearest-neighbour cosine | **0.816** |

Real embeddings are **clustered**, not isotropic: a chunk's nearest neighbour is
at 0.82 while two random chunks sit at 0.46. That is the condition routing needs,
and it is why the numbers below look nothing like the synthetic isotropic row
(12% recall at low `nprobe`).

### The index on that corpus

| nprobe | rows scored | p50 | p95 | recall@10 |
|---|---|---|---|---|
| 1 | 117 | 0.18 ms | 0.28 ms | 64% |
| 2 | 234 | 0.21 ms | 0.25 ms | 79% |
| 4 | 468 | 0.27 ms | 0.69 ms | 91% |
| 8 | 936 | 0.41 ms | 0.56 ms | **98%** |
| 16 | 1,872 | 0.59 ms | 0.79 ms | **100%** |
| all 19 cells | 2,223 | 0.94 ms | 5.86 ms | 100% |

**At the default setting — 10% of cells, `nprobe` 2 of 19 — this corpus gets 79%
recall@10 in 0.21 ms.** Opening 8 of 19 cells reaches 98% in 0.41 ms.

Two things follow, and the second matters more than the first:

1. The index is doing its job on real data: 98% recall while scoring 936 of 2,373
   rows is the trade it was built for.
2. **The synthetic isotropic row in the tables above is not a description of any
   real corpus.** It is a stress test, and it should be read as one. A corpus of
   text embedded by a real model is clustered; the pathological case has to be
   constructed deliberately.

```bash
pip install model2vec
python bench/real_corpus.py
```

Small-corpus caveat, stated: 2,373 chunks is 19 cells, so `nprobe` 2 is 10% of
the cells but only 234 rows. At a million chunks the same 10% is 100,000 rows,
and the latency moves with the rows, not with the corpus.

## `retrieve()`: where the time actually went

With the address ranking at 2.5 ms, `bench/retrieve_stages.py` asked the next
question: what is the rest of the query? The answer was not the algorithm. A
`cProfile` run over 80 queries showed **5,120 `execute` calls and 4,960
`fetchone` calls** — 62 of each per query.

That was an **N+1**: after fusion, every candidate chunk was hydrated with its own
`SELECT … WHERE chunk_id = ?`. Sixty candidates, sixty round trips, to fetch
sixty rows.

| | before | after |
|---|---|---|
| `retrieve()` p50 | 11.76 ms | **5.88 ms** |
| `retrieve()` p95 | 28.42 ms | **6.73 ms** |
| `execute` calls per query | 64 | **5** |
| hydration queries per query | 60 | **1** |

The p95 is the number that matters for a server: **4× better tail**, because the
tail was the sum of sixty round trips and now it is one.

### What is left

| stage | p50 | share |
|---|---|---|
| embed (model2vec, one short query) | 0.17 ms | 3% |
| bm25 (FTS5, 60 candidates) | 1.94 ms | 33% |
| vector (60 candidates, from SQLite) | 1.67 ms | 28% |
| fusion + hydration + rerank | ~2.1 ms | 36% |

`bm25` and the vector read are now the two real costs, and both are the same
kind of thing: reading 60 rows out of SQLite. That is where the next
optimisation goes, and it is worth saying plainly that it is a *constant factor*
— the algorithm is no longer the problem at this size.

```bash
python bench/retrieve_stages.py
```

A regression test guards the shape, not the speed: `retrieve()` must issue
**one** hydration statement, because the failure mode here is a silent slowdown
with correct answers.
